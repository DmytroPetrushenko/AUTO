# Другий етап

## Схема та міграція

Міграція `0004` додає версії персоналу, нормалізований особистий номер,
МВО автомобіля, типізовані періоди `vehicle_history`, погодження дублікатів
і незмінні знімки застосованих зовнішніх документів.
Єдина таблиця періодів розрізняє підрозділ, службу, МВО, стан/статус/експлуатацію
та чотири ідентифікатори. Посилання на довідники захищено FK.
Інтервали напіввідкриті `[valid_from, valid_to)`; NULL початку означає невідому
фактичну дату. Початкова історія міграції не використовує дати created_at,
accounting_date або сьогодні замість невідомої дати.

Перед міграцією перевіряються дублікати особистих номерів: неоднозначні дані
блокують оновлення без автоматичного злиття. Таблиці vehicles/personnel
розширюються без видалення таблиць або вимикання foreign_keys.
Копія SQLite перевіряється integrity_check і foreign_key_check;
дерево локальних вкладень також копіюється, якщо є.

Перевірено заповнену синтетичну БД версії 0003, її окрему тестову копію,
збереження кількості автомобілів, персоналу, ID та зовнішніх зв'язків,
невідомих дат і відмову при дубльованих особистих номерах.
Після перевірки копії локальної БД зроблено перевірений backup та виконано
локальну міграцію до 0004. Excel і реальні дані не імпортувалися.

## Бізнес-операції

Додано `auto/history.py` та `auto/personnel.py`. Картка створює початкову
історію з невідомою датою або явно заданою датою. Зміна датованих полів
наявної картки вимагає дату; перегляд не пише дані. Підтвердження перевіряє
відбиток вхідних полів, періодів, версії, користувача, дублікатів і документів;
застарілий перегляд відхиляється. Межі сусідніх періодів узгоджуються однією
транзакцією BEGIN IMMEDIATE. Майбутні події враховуються в проєкції стану на дату.

Повтори VIN/шасі/заводського номера погоджує адміністратор; військового номера —
оператор або адміністратор. Потрібні явне підтвердження, причина, список карток
зі збігом; погодження незмінне та є в аудиті. Пошук охоплює історію й архів.
Незмінені раніше погоджені ID не заважають редагуванню інших характеристик.

Персонал має перевірку імен, особистих номерів, активності та версії.
Оператор додає; адміністратор редагує/деактивує. МВО — окремий FK і періоди,
пошук реєстру враховує ПІБ. Права перевіряються в сервісах.
Видалення помилкової картки доступне адміністратору з підтвердженням і причиною;
початкова автоматична історія не блокує, самостійні історичні події,
погодження й застосовані документи блокують. Списані/втрачені картки не видаляються;
аудит з ID, ідентифікаторами й причиною залишається.

Інтерфейс `register_document_lock` зберігає незмінний знімок стану на дату
зовнішнього застосованого документа. Зміни історії, які суперечать знімку,
показують конкретні посилання й блокуються. Повного модуля дорожніх листів немає.
Зняття такого захисту UI не пропонує; узгоджене виправлення потребуватиме
реального майбутнього модуля документів.

Перевірено 69 тестів сервісів/міграцій, Ruff без помилок. Схема:
`59bb47d2c4d61604440bdfcae7c96438c85a00b4`, push і SHA GitHub перевірено.

## Інтерфейс і підсумкова перевірка

Додано `auto/ui_history.py`; оновлено `auto/ui.py`. Персонал має форму
створення/редагування, активність і перегляд аудиту; МВО є у вкладці «Облік»
та пошуку реєстру. Дата події явно вводиться, без значення за замовчуванням.
Наявні періоди можна виправляти через окремий перегляд; сусідні межі видно
до запису. Усі погодження вимагають checkbox та причину; заборонені ролі
блокуються в UI й повторно в сервісах. Доступний перехід до карток зі збігами.

Перехід із перегляду історії не зберігає її мовчки: користувач підтверджує
саме показані історичні зміни. Підтверджений запис завершує відкладений перехід.
Фільтри аудиту: користувач, тип зміни, діапазон UTC-дат. Ролі лишаються
конфігурацією локального довіреного процесу; мережевої автентифікації немає.

Повний набір із 92 тестів пройшов. Після уточнення точного правила видалення
переданих помилкових карток додано ще 2 тести та повторно перевірено пов'язані
сценарії історії й UI. Поточний набір — 94 тести, включно з 21 UI-сценарієм.
Ruff, pip check та git diff --check пройшли перед фінальним комітом.
Окремо 4 пов'язані тести підтвердили, що знімки аудиту використовують реальні
UUID збережених періодів при створенні та виправленні історії.
У браузері на localhost вручну перевірено реєстр, порожню дату події,
вибір МВО та форму персоналу; дані під час цієї перевірки не записувалися.

Знімок застосованого документа зберігає також ПІБ/реквізити МВО на час
застосування, тож перейменування особи не переписує старий документ.
Локальна БД має версію 0004, 0 автомобілів і 0 осіб, integrity_check=ok,
foreign_key_check без порушень. Backup перед міграцією перевірено.

Крок бізнес-операцій: `73f7a03d15d9d89358aeeb0ac67c967ac302fae1`, push і SHA
GitHub підтверджено. Змінені файли цього етапу: `auto/models.py`,
`auto/schemas.py`, `auto/services.py`, `auto/history.py`, `auto/personnel.py`,
`auto/ui.py`, `auto/ui_history.py`, міграція 0004, тести міграції/історії/сервісів/UI,
README та цей звіт.

Наступні етапи: документи/вкладення, обладнання, версійні примітки,
показники й норми; Excel і створення на основі — окремо. Повний модуль
дорожніх листів та імпорт реальних Excel у цьому етапі не створювалися.
