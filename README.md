# AUTO

Локальний реєстр автомобілів та іншої колісної техніки. Python 3.12,
Streamlit, SQLModel, SQLite, Alembic. Реальні дані до репозиторію не додаються.

## Windows PowerShell

Усі команди виконуються з `C:\Users\dpetr\Projects\AUTO`; активація venv не потрібна.

```powershell
& .\.venv\Scripts\python.exe -m pip install -r requirements.lock
& .\.venv\Scripts\python.exe -m pip install --no-deps -e .
& .\.venv\Scripts\python.exe -m auto.cli migrate
& .\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1
```

`migrate` створює нову порожню БД і початкові класифікатори. Автомобілі,
марки, моделі, підрозділи й персонал автоматично не створюються.
Типова БД: `data/auto.sqlite3`. Інший шлях задається змінною `AUTO_DB_PATH`.
Запуск UI не змінює схему: міграції виконуються окремою командою.

```powershell
& .\.venv\Scripts\python.exe -m pytest
& .\.venv\Scripts\python.exe -m ruff check .
```

Залежності та інструменти тестування зафіксовано в `requirements.lock`.
Тести створюють окремі тимчасові БД та не використовують робочу базу.
Межі реалізації та план описано в [docs/architecture.md](docs/architecture.md).

## Перший етап

Реєстр підтримує пошук за ідентифікаторами, маркою/моделлю, фільтри,
архівні статуси, сортування та вибір колонок. Картка має сім вкладок;
редагування основних/технічних/облікових полів, загальний аудит змін,
збереження всієї картки й скасування. Довідники доступні з меню та через «+».
Зміни між вкладками зберігаються в чернетці, вихід із нею потребує вибору дії.
Чернетки не переживають закриття браузера/завершення процесу.

За замовчуванням локальний користувач Windows працює як адміністратор.
Для іншого режиму задайте перед запуском `AUTO_USER_ID` та
`AUTO_ROLE` (`admin`, `operator`, `viewer`). Роль перевіряється в бізнес-операціях.
Це локальна конфігурація довіреного процесу, а не система входу для мережі.
Використовуйте прив'язку до `127.0.0.1`, як у команді вище.

Документи, обладнання та примітки поки показують повідомлення про наступний етап.
Показники, норми, Excel і створення на основі
ще не реалізовані. Детальний звіт: [docs/stage1-status.md](docs/stage1-status.md).

## Другий етап

Персонал: додавання, редагування адміністратором, деактивація, перевірка особистого
номера та аудит. МВО обирається у вкладці «Облік»; створення особи — через
«Довідники → Персонал». Реєстр шукає також за ПІБ МВО.

Підрозділ, служба, МВО, статуси/експлуатація та ідентифікатори мають датовані
періоди у вкладці «Історія». Невідома початкова дата залишається порожньою.
Для зміни датованих полів картки вкажіть фактичну дату, натисніть «Зберегти»,
перегляньте «було → стане», поставте підтвердження та натисніть
«Підтвердити та зберегти». Там само можна виправити дату й значення наявного
періоду; межі сусідів узгоджуються атомарно. Майбутні події відображаються
як поточний стан лише після настання дати. Стан на дату не редагується окремо.

Збіги ID показують конкретні картки. Для повтору військового номера потрібні
причина й підтвердження оператора/адміністратора; фізичні ID погоджує лише
адміністратор. Погодження та зміни залишаються в аудиті. Картка перевіряє
версію й актуальність перегляду перед записом.

Адміністратор може видалити лише помилкову картку без самостійних записів,
із причиною та підтвердженням. Початкова автоматична історія не блокує;
списані/втрачені картки й картки з блокуючими зв'язками не видаляються.

Повний модуль дорожніх листів відкладений. Є інтеграційний контракт захищеного
знімка застосованого документа; конфліктна зміна показує посилання на нього
та блокує транзакцію. Докладно: [docs/stage2-status.md](docs/stage2-status.md).

Для кожного push GitHub Actions запускає Ruff і pytest на Windows / Python 3.12.
